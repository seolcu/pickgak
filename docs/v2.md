# PickGak v2: desktop app (alpha)

v2 moves PickGak from the browser into a small desktop app.
- **Why**: a browser tab can't see keys pressed in the game, can't stay on top of it, and continuous screen sharing costs performance.
- **What it does**: when you hold TAB in game, it takes one screenshot of the game window, reads the scoreboard, fills the board, and shows the advice in a small overlay.

## Safety

PickGak never touches the game process: it injects nothing and reads no memory, packets or game files.

| What | How | Like |
| --- | --- | --- |
| Seeing TAB | Linux: XInput2 *raw* key events on the X server. Windows: a low-level keyboard hook. Both only observe; the key still goes to the game | OBS hotkeys, push-to-talk |
| The screenshot | `GetImage` of the game's own window (Linux) or Windows Graphics Capture of it (Windows) when TAB has been held 0.3 s (0.6 s on Windows), then every 1.5 s while held. Windows keeps taking frames for up to 3 s until the frame really is the scoreboard, and never emits the gameplay frame before it | Taking a screenshot |
| Recommendations | The PickGak API (public stats) | The website |

**Keyboard**: only TAB is acted on. Every other key event is dropped as it arrives; nothing is logged or stored.

## Privacy

- Captures stay on your computer (`~/.local/share/com.seolcu.pickgak/captures`, last 50). Nothing is uploaded.
- Your portrait corrections ("teach once") are stored in `templates.json` in the same folder.
- The app talks only to `https://pickgak.seolcu.com/api`.

## How it works

```
TAB held 0.3 s (0.6 s on Windows) ─► grab game window ─► is it the scoreboard? ─► read portraits, numbers, my row
                                                                        │ no: retry while the same press lasts (Windows, up to 3 s)
                       overlay (top picks, threat, bans) ◄─ board ◄─────┘ (auto-fill, undo)
```

On Windows the scoreboard can fade in after the first frame, and Windows Graphics Capture can hand back a frame from just before TAB. A frame only becomes a reading if the scoreboard is actually in it; a press that ends too early reports "released before the scoreboard" in the debug log instead of reading the gameplay screen.

**Scoreboard layout** (`app/crates/vision`) is inferred on every capture, because it differs by mode: a 5v5 match, the practice range (5 + 1 rows, lower and larger) and open queue 6v6.
- The light-gray header bar gives the table's top and left/right edges. Ult-ready rows glow blue to the left of the table and perk columns shift it, so the team colors aren't used for the edges.
- Below it, the blue (ally) and red (enemy) bands give the rows. The row height is twice the distance from a band's top to its first role icon.
- Portrait boxes and number columns scale with the row height.
- Killcam and play-of-the-game frames are rejected.

**Portraits**: the scoreboard shows each hero's "2D portrait" art.
- Built in: one 32x32 thumbnail per hero, cut from that art as hosted on Namu Wiki (`app/scripts/make-seeds.py`). It is composited onto the row's own background color before comparing. A match needs a score of 0.5 or more and a lead of 0.1 or more over the next hero. On the fixtures the right hero scores 0.58–0.94 and leads by 0.11 or more.
- Built in too: "?" and empty practice-range rows (`examples/make_states.rs`). Respawn timers score under 0.31 and stay unread.
- Corrections: naming a portrait in the app ("teach once") overrides the built-in result from then on (0.94–0.98 for the same art).

**Dead players**: the scoreboard keeps a dead player's portrait, darkened, under a skull and then a respawn timer. The skull is a built-in state; the hero around it is matched with the middle masked out (score 0.7+, lead 0.12+; a wrong hero reached at most 0.66 on the captures). Otherwise the board keeps the hero it had.

**Placement tolerance**: each portrait is compared at 25 small shifts (up to 2/44 of a row each way) and the best one counts. A one-pixel misplacement used to move a score by up to 0.3.

**Bans** (competitive): the red-framed icons at the top left of the TAB screen. They are Nexon's hero thumbnails (`bans.bin`, from the API's `thumbnail`), not the scoreboard portraits: 0.70-0.89 for the right hero, a lead of 0.38+, on every competitive TAB capture. Any number from 1 to the lobby-ban maximum is accepted (fewer bans happen when votes fall short); more than the base count turns the lobby ban on. Nothing changes if an icon isn't recognized.

**Rank range** (competitive): the "match rank range" emblems under the timer at the top right. They are the tier emblems (`ranks.bin`); same-shape emblems (silver and gold) are told apart by color, so the score is shape similarity minus 4 x the distance in mean chromaticity. Read correctly on all 43 competitive TAB captures (bronze-silver, silver-silver). A range sets the stats filter to competitive and every tier it spans (`bronze+silver`; champion uses grandmaster stats). The server merges tiers assuming equal match counts per tier (Nexon doesn't publish them): pick and ban rates are averaged, win rates weighted by pick rate. Placement matches show no emblems and leave the filter alone.

**Map**: the "mode | map" text at the top right of the TAB screen. The map name is read by the bundled Tesseract from the whole "mode | map" block (thresholds 110 and 130, 8x upscale, `kor+eng`, `--psm 7`), and the map name is matched as the block's suffix. The mode gives the line enough context: on a 2560x1440 capture the tight `콜로세오` read badly, while the full `밀기 | 콜로세오` block read `콜로세오` exactly. `왕의 길` and `사모아` also rank first. The map name is compared only to the map list sent by the UI, so a wrong map is asked for instead of guessed. The OCR worker runs after the capture is emitted. Its answer (including "no map") is cached by map text, matched by similarity (`MAP_MIN`), because the same text differs by a few pixels between captures: an exact key made every repeat TAB run Tesseract again. A map the user picks on the reading bar is remembered for that map text (`maps-taught.json`) and wins over OCR from then on, so a correction sticks. 2.9.0's `maps.json` is ignored: its stats map filter taught it, and many maps were stored as Grimsvotn or Junkertown. While OCR is reading a new map text the capture carries no map, never the previous one; the main window keeps the last known map for new-match detection and only follows a map when the reading changes, so a map picked by hand survives repeat captures.

The map selector in the reading bar shows the map the OCR read, and corrects it: choosing a map replaces the fingerprint for that screen, updates the kept captures and makes that screen resolve to the map from then on. The stats filter follows the recognized map; only captures taken after "New match" and within 20 minutes are used for map teaching, and never the practice range.

**Overlay**: always on and click-through. "Only while TAB" hides its content instead of the window, because showing and hiding the window could take focus from the game. Unlock it from the main window to move it.

**Party marker**: a bright green strip just left of an ally row. Measured at 2560x1440: the two party rows had 0.53 and 0.55 of the sampled strip green, every other row 0.00-0.01, so the detector asks for 0.25 (`PARTY_MIN`). Ally rows only; the enemy team has no marker.

**Party identity (green + name, never a guess)**: a player is assigned only when both hold: the row has the green marker and its name matches the name image already confirmed for a Players-tab profile. Preferred heroes are never used (another player can pick the same hero, and a party member does not have to pick a preferred hero).

- **Name image**: the bright glyph mask of the name line, with the colored nameplate, level emblem and dim title line below excluded. It is resampled to a 64x16 grid, mean-subtracted and unit length. On two real recordings the same name scored 1.00 at the same resolution, 0.76-0.98 at 1080p and 0.53-0.96 at 720p; different names stayed at or below 0.31, except a pair differing by one syllable (0.815). Automatic matching needs 0.90 and a 0.10 lead, so a resolution change asks once more instead of guessing.
- **What stays out of the name image**: the ult circle left of an ally's name (its ring, check mark and percentage are as bright as the glyphs) appeared on 35 of 274 party rows in three recordings and dropped the same name to 0.32; glyph parts that start in the first 0.21 row heights of the band are now left out (a name starts at 0.27-0.32). A frame caught while the scoreboard fades in (glyphs peaking at 228-231 instead of 255) scored 0.55-0.88, so a name dimmer than 240 is left unread for that capture.
- **Kept for the match**: once a row is assigned (a matched image or an answer), a later capture that does not recognize the name does not undo it. The same name still varies between captures (0.86-0.94 for one name at one resolution when the scoreboard sits a few pixels elsewhere), and before this every such capture freed the row and asked again. The row is freed only when its name points at another registered player, matches none of them, or the answer is undone in the overlay.
- **First time**: `tesseract` (Korean + English data) reads the name column as a suggestion. Two preprocessing passes (counter-shear straightening the italic font, threshold 150, nearest 5x upscale, 5 px white left margin) ranked the right registered name first for 10/10 names on the 2560x1440 app capture (0.57-0.92). OCR is only a suggestion; nothing is assigned until the overlay question is answered.
- **Question in the overlay**: "Is this 'name'?" with yes / no / later. The overlay accepts the mouse only while the question (and the short undo window) is open, then goes back to click-through. The name image makes an accidental yes unlikely; a 6-second undo removes the just-learned image, and the main window's party card can re-pick later.
- **No question when the name is too different**: if neither the OCR text nor a confirmed image is close to a registered name, no prompt appears. The main window shows a small "Confirm party" button that opens the manual picker; an unknown player can be marked "not a registered player", which stops the question for the session.
- **Storage**: `names.json` in the app data dir, local only, up to 6 name images per player. Nothing leaves the computer.
- **OCR packaging**: every Linux package (rpm, deb, AppImage) and the Flatpak bundle the same fully static Tesseract 5.5.3 + Leptonica 1.87.0 + `tessdata_fast` (`kor`, `eng`). The Windows installer bundles the official Tesseract 5.5.3 build plus the same data. Nothing needs to be installed on the host; `status.ocr_bundled` shows whether the running binary came from the package or PATH.
- **OCR performance**: Tesseract never runs on the capture thread. The capture emits immediately; one low-priority worker runs at most one Tesseract process at a time with `OMP_THREAD_LIMIT=1`, a 2-second timeout, and tessdata_fast. OCR runs only for a party row with no visual name match (visual-first), and the text is cached by the glyph fingerprint plus a near-identical fingerprint cache. A second preprocessing pass only runs when the first is weak. The map OCR is cached per map text and likewise off the capture path.

**Recommendations**: personal picks and party combos are separate views. Personal picks are always calculated for me against the board as it is now, including party members' current picks. Party combos recommend a hero for every party member regardless of what they have picked; a member who picked is not locked, because they can change their mind. The main window has a "My picks" / "Party combos" switch, and the overlay shows both blocks at once. Both views use the same per-player "preferred only" star as the rest of the app; the overlay used to ignore it, which made its list differ from the main window. A small "preferred only" tag now appears in both places when it is on. Applying a combo is an explicit action and can replace a party member's current hero.

**Overlay content**: phase, map, my picks, the party combos (all of them, each with its synergies and per-pick reasons), threats, party members and how many party rows still need a name, role counts for both teams, and the banned heroes once the ban phase is over. During the ban phase the three vote picks and the rest of the candidates replace the picks. The overlay uses the same lists, scores, role icons, tiers and reason chips as the main window, and the same per-person "preferred only" setting; it used to cut the lists to three picks and one combo, which made the same board look different in the two places. It reads the same board and TAB reading as the main window and never writes the board.

The overlay is click-through, so the mouse wheel never reaches it: the window grows and shrinks to the height of its content (capped at the monitor), instead of scrolling. Its own header shows the map the recommendations were asked for, not the last capture's map, so the header and the reasons always agree.

**Desktop home**: the board is read-only and filled from TAB only. "Edit" opens the old editor as a drawer for corrections. Settings > During matches switches between the Coach (recommendations first), Board (board and recommendations side by side) and Hub (overlay preview + board) layouts. Smurf suspects are marked as threats automatically; turning one off in the editor keeps it off for that match.

**My row**: the highlighted ally row. PickGak moves "me" to that slot, so the left/right damage slot matches the game.

## Edge cases handled

| Case | Behavior |
| --- | --- |
| TAB pressed in another app (browser, chat, a Wayland window) | Ignored: TAB counts only while `_NET_ACTIVE_WINDOW` is the game (no capture, no overlay). GNOME deletes the property while a Wayland window has focus, so a missing value counts as "not the game" when the window manager advertises it; without EWMH at all it isn't blocked |
| TAB released while another window had focus | Each repeat re-checks the real key state and the focus, and stops; a press is capped at 120 s |
| Processing slower than the repeat | Only the newest pending capture is read |
| Holding TAB | Repeats that read the same as the last saved capture aren't written to disk for 20 s; the folder keeps 100 |
| Game minimized (grab fails) | Reported once per press |
| A hero, ban or filter fixed by hand | Kept: the board takes only what changed on screen since the previous capture. "New match" starts fresh |
| App restarted | The last capture of the previous session isn't put on the board (only captures under 5 minutes old) |
| A new match starts | The board is cleared automatically: the map, hero bans or rank range on the TAB screen changing, or the team's total eliminations dropping, means a new match. "New match" still works, and the automatic clear can be undone from the toast |
| Same map in quick play and competitive | Only the map name right of "\|" is compared, so one pick covers both |
| 4K, 1080p, 21:9 | Geometry is relative to the height and the table; fixtures scaled to 3840x2160 and 1920x1080 and pillarboxed to 3440x1440 read the same |
| Deathmatch, custom boards | More than 6 rows a side isn't treated as a team scoreboard |
| Empty ban slots | Skipped; bans apply only when every shown icon is recognized |
| KDE Plasma: the focused full-screen game sits above "keep above" windows | The locked overlay is an on-screen-display window, the one KWin layer above an active full-screen window (see `kde_layer.rs` for the measured layers). KWin centers such a window when it maps it, so the overlay is put back where it was; unlocked, it is a normal window again so it can be dragged |
| PickGak started a second time | The running copy shows its main window and the new one exits, so TAB is never captured twice. After an update the new copy waits for the old one to exit |

Not covered yet (no captures): colorblind filters (team colors may change), open-queue 6v6, the hero-select screen.

`cargo run --release -p pickgak-vision --example read_dir -- <folder>` prints what the app reads from a folder of captures, for regression checks.

| Check | Result |
| --- | --- |

| One TAB capture (grab + read + UI update) | ~270 ms CPU total, only on TAB |
| Window grab 1280×720 | 40 ms |
| Memory (app + WebKit processes) | ~940 MB reported; this display has no GPU (software rendering) and shared memory is counted per process. Re-measure on a real desktop |

## Known limits (alpha)

- **Linux X11/XWayland and Windows 10 1903+.** On Linux, Overwatch under Proton is an XWayland window (confirmed on the target PC); the app itself runs on XWayland so "always on top" works under GNOME. KDE Plasma 6 (KWin) needs the overlay typed as an on-screen display instead (confirmed on Fedora 45, Plasma 6.8.2). Windows uses a low-level keyboard hook and Windows Graphics Capture (HDR screens can shift colours).
- **Confirmed with the real game (Linux)**: TAB detection and the window grab (2560x1440, not black). **Not yet measured**: the real FPS impact. **Windows capture has not been tested with the game yet**; it is built in CI.
- **Updates**: rpm/deb installs go through `pkexec dnf/apt`; AppImage replaces its own file; the Windows installer runs silently; Flatpak only points at `flatpak update`. A file is only run when its SHA-256 matches the published one.
- **Overlay**: shows over borderless windowed mode. Exclusive fullscreen may hide it: no external window can be drawn over a game that owns the display. The overlay is raised again on every TAB press and every capture without taking focus; the debug view reports whether the window is visible and topmost, and (Windows) whether a Direct3D full-screen app was detected at the last TAB press.
  - Locked overlays (Windows and Linux) fit beside the detected scoreboard when the captured game fills the overlay's monitor. At 1080p the window starts at (20, 88), below the tab bar, and fills the margin up to 13 pixels before the scoreboard edge, at most 520 pixels wide. The edge moves with the match state: x=290 in a match and x=551 before it (2560x1440 captures scaled to 1080p; another 1920x1080 capture measured 281), so the panel widens and narrows with it. Insets, width and webview zoom scale with frame height, independent of desktop scaling. A margin narrower than 248 pixels shrinks the content to fit; height still follows the content. Unlocking preserves manual positioning. Windowed captures keep their manual placement because their screen origin is not known.
- **Board auto-fill**: only teams whose row count matches the board (the practice-range bot row is read but not put on the board). A hero whose row doesn't match its slot role goes to a free slot of its role, and "me" follows my hero (in the practice range my row is always on top). Open queue 6v6 is read but untested.
- **Smurf hints**: 5v5 only (same-role comparison).
- **Not yet built**: map from the hero-select screen.

## Build

```bash
docker build -t pickgak-app-build app/docker
docker run --rm -v "$PWD":/repo -v pickgak-cargo:/cargo -v pickgak-target:/target \
  -v pickgak-npm:/root/.npm -w /repo/app pickgak-app-build scripts/build-linux.sh
# -> app/dist/PickGak-2.6.0-1.x86_64.rpm, PickGak_2.6.0_amd64.deb and PickGak_2.6.0_amd64.AppImage
```

The Windows NSIS installer is cross-built on Linux by `app/scripts/build-windows.sh` (cargo-xwin). It bundles the
official Windows Tesseract build, unpacked from its installer and pinned by hash. The release workflow
attaches it as `PickGak_<version>_x64-setup.exe` to the GitHub release next to the Linux packages, where
the download page and the in-app updater see it. Nothing starts it in CI: the Windows VM checks it used to run (silent install, OCR smoke,
overlay window) passed while real PCs still hit bugs, so a real Windows PC is the test.

## Flatpak

The Flatpak repository is published on GitHub Pages by the release workflow and signed with a dedicated
key (the private key is the `FLATPAK_GPG_PRIVATE_KEY` GitHub secret; the owner keeps offline backups). It
used to be served by the API under `/api/flatpak`, which now redirects there. Users add it once:

```bash
flatpak remote-add --if-not-exists pickgak https://seolcu.github.io/pickgak/flatpak/com.seolcu.pickgak.flatpakrepo
flatpak install pickgak com.seolcu.pickgak
```

Updates come from the same repository (`flatpak update com.seolcu.pickgak` or GNOME Software); the app
detects Flatpak and only shows that command. The Flatpak build is made with `--no-default-features`: the
GNOME runtime has no libappindicator, so it has no tray icon. The main window has the lock button, and
closing it quits. `app/flatpak/build-repo.sh` lays the prebuilt files out and exports them with
`flatpak build-finish` and `build-export` instead of flatpak-builder, so it needs no bubblewrap and runs in
an unprivileged container. `app/scripts/build-linux-release.sh` checks the bundled Tesseract and starts
the same binary on a virtual display outside the sandbox, then leaves the repository in `app/flatpak/repo`.

Tests:
- `cargo test -p pickgak-vision -p pickgak-live` (in `app/`)
- `app/scripts/e2e-live.sh`: TAB on a virtual display
- `app/scripts/e2e-app.sh`: the whole app
- `app/scripts/e2e-overlay-drag.sh`: the overlay moves when unlocked and stays put when locked
- `app/scripts/e2e-perf.sh`: CPU and overlay

## Trying it with the game

1. Install: Fedora `sudo dnf install ./app/dist/PickGak-2.6.0-1.x86_64.rpm`, Debian/Ubuntu `sudo apt install ./app/dist/PickGak_2.6.0_amd64.deb`, or run the AppImage. On Windows, run `PickGak_2.6.0_x64-setup.exe` (Windows 10 1903+). Then start "PickGak".
2. Play in borderless windowed mode. Hold TAB for about half a second.
3. Heroes are recognized out of the box. If one is misread, open the latest capture in the "TAB reading" bar and correct it once.
4. The overlay is already on. Turn on "Only while TAB" if you want it hidden during play.

## Debug view (testing)

The "TAB reading" bar has a debug toggle at its right end (the bug icon). It stays on or off across restarts.

- **Event log**: TAB presses and releases, presses ignored because another window had focus (with that window's title), capture failures, and the grab and read time of every capture.
- **What the last capture was read from**: the thumbnail with the detected table edge (yellow), portrait boxes (green when a hero was read, red when not), ban and rank boxes (blue) and the map text block (purple). Each box is labelled with the hero, its score (0-100) and the first three numbers.
- **Copy report**: log and the last capture's geometry, labels and numbers as JSON on the clipboard. Images are never included. Window titles can be, so read the text before sharing it. The report also says whether the overlay window is visible and topmost, so "the overlay never shows up" can be told apart from a capture problem.
- **Open captures folder**: `~/.local/share/com.seolcu.pickgak/captures` (the newest 100 full-resolution frames, local only).

**Probe only** (no install): `cargo run --release -p pickgak-live --example probe` prints, for each TAB press:
- whether TAB was seen
- the grab time
- whether the frame is a scoreboard

It also saves the capture.
